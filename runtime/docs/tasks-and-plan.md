# Skill Hub 首版任务与执行计划

日期：2026-10-14
状态：实施中，实际完成情况见 [实施记录](progress.md)
范围依据：[架构与实施方案](architecture-and-plan.md)

首版交付自建插件市场与 MCP 服务，完成 Codex、Kimi 桌面应用、ZCode 三类客户端的安装、更新、回滚及新会话加载。Claude Code 后续接入。

## 1. 执行方式

按依赖与里程碑推进，不先指定缺少人员配置依据的日历工期。每个任务应有代码或文档交付物、验证证据与明确完成标准。任务初始状态为待办，最新状态以实施记录为准；完成时记录实际产物和验证结果。

任务状态使用：待办、进行中、待验证、完成、阻塞。客户端能力未确认、缺少真实环境或没有加载证据，不能标为完成。任务执行中产生的范围调整应同步回架构文档。

实施记录建议保存到 `docs/progress.md`，每条记录包括任务 ID、状态、产物路径、验证结果和剩余问题。此计划不创建外部工单或新的 Codex 聊天。

## 2. 里程碑与发布门槛

| 里程碑 | 对应阶段 | 目标 | 通过条件 |
|---|---|---|---|
| M0 接入路线确定 | P0 | 三类客户端有可执行接入方案 | 确定真实客户端形态、版本、加载入口与最小样例证据 |
| M1 内容可发布 | P1 | 内容修订到不可变产物 | 可构建、校验、发布和回滚，历史内容不被草稿改变 |
| M2 首条链路跑通 | P2 | Codex 完整接入 | 本地安装、更新、新会话加载、诊断和失败恢复通过 |
| M3 首版功能齐备 | P3 | 市场、MCP、三类客户端可用 | 用户可从市场完成安装，三类适配器均有真实验证 |
| M4 首版可交付 | P4 | 稳定性和完整验收 | 验收矩阵全部通过，部署、备份恢复与使用文档齐备 |

Codex 作为第一条实现链路；Kimi 和 ZCode 在 M0 同时完成调查，不能推迟到后台完成后才寻找加载入口。若某客户端无法自动加载，先记录缺口和补齐方式；仅手动查询不能算满足原定的新会话加载目标。

## 4. 推荐执行顺序

1. 第一批：T01，随后验证 T02、T03、T04，并建立 T06 工程基础；通过 M0。
2. 第二批：T05、T07–T12，形成可发布内容与下载接口；通过 M1。
3. 第三批：T13–T17，先完成 Codex 全链路；通过 M2。
4. 第四批：T18–T24，建设市场与 MCP，完成 Kimi、ZCode 适配；T25 联调后通过 M3。
5. 第五批：T26–T29，执行故障、恢复和真实客户端验收；通过 M4。

任务依赖满足后，市场页面、MCP 与不同适配器的实现可以独立推进。此处描述工作依赖，不自动创建并行 Agent 或外部任务。

关键路径：客户端入口验证 → 数据契约 → 内容构建 → 发布与授权 → 本地安装事务 → 三类适配器 → 市场联调 → 完整验收。客户端自动加载和会话固定能力是最早需要消除的不确定性。
